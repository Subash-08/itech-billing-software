# Storage plan final review and execution corrections

Review date: 2026-09-17. Source and plan inspected; no application implementation or automated suite run in this review. One read-only Cloudinary Admin request using local project environment credentials returned HTTP 200. This establishes local credential authentication only, not Vercel configuration or image/PDF upload/delete permissions. No assets changed. Credentials previously disclosed in conversation must be rotated through the provider and replaced in environment configuration; do not copy them into code or this document.

Proceed with the storage/auth implementation after incorporating these corrections. Read VERCEL-STORAGE-REVIEW-AND-IMPLEMENTATION.md as the parent specification.

1. **No circular auth dependency.** auth.ts already imports better-auth.ts. Put getTrustedOrigins/canonical origin parsing in a new server-only origins.ts with no imports from either auth module. Both modules import it. Require valid explicit production configuration, no hardcoded fallback. If APP_ORIGIN and BETTER_AUTH_URL disagree, fail with a safe configuration error. Validate HTTPS, exact origins, no userinfo/query/fragments/unexpected paths/wildcards; normalize and deduplicate explicit additional origins. No request-header trust. Separate preview and production environment/DB/storage decisions.

2. **Keep the real file contract.** The application uses collection `files`, not proposed `storedFiles`. Promote pending uploads into `files` preserving IDs consumed by company logos, invoice snapshots, purchase attachments, services and warranty images. Map Cloudinary API `type: authenticated` correctly; don't assume resource metadata has a `delivery_type` property. Do not create a second disconnected file collection.

3. **Prevent signed-upload replay and replacement.** Sign immutable public_id, type authenticated, overwrite false, approved preset/restrictions and fixed folder/account. Never sign arbitrary caller-supplied parameters, transformations or delivery types. Cloudinary upload signatures exclude file and resource_type and remain valid independently of application pending expiration; a pending record alone does not enforce provider permissions or expiration. Use provider-enforced size/format restrictions where available, quota/rate limits and delayed orphan cleanup after the signature window. Detect assets uploaded under unexpected resource types. Never allow a replay to replace an Active asset after verification.

4. **Validate completion thoroughly.** Use only the pending record to select tenant/user/connection/asset; do not trust the client response URL, public ID, MIME, size or claimed completion. Query the provider using the pinned connection, verify immutable asset identity/type/version, server-side byte size, permitted format and authenticated delivery. Check content signatures through bounded provider fetches or a verification worker. Pending/quarantined assets are not attachable or downloadable. Promote files and mark pending completion atomically in Mongo with a unique pending/file relationship. Concurrent completion/retry returns the same file; expired/cross-tenant/tampered completion fails. Capture verified checksum if used, not a client assertion. Don't hold a Mongo transaction open during provider network requests; revalidate versions when committing.

5. **Wire every caller to the upload flow.** Add a shared frontend upload helper for prepare -> Cloudinary -> complete with progress, cancellation, recoverable retry and error states. Use it for company logo, template logo where applicable, purchase attachments, service intake/update photos and warranty evidence. Updating endpoints alone does not make existing multipart forms support 5 MB on Vercel. Keep a separately bounded legacy multipart path; ensure request overhead stays below the platform limit. Update download handlers to actually stream rather than use arrayBuffer. Validate source host, prevent redirects to untrusted destinations, limit time/bytes/concurrency, and stop upstream work on disconnect.

6. **Reauthentication matches actual passwords.** Better Auth login hashes and the custom server/security.ts profit-password verifier are distinct. Verify the current authenticated user's credential-provider account with the same verifier as login, normalizing user ID consistently. Never use profitPasswordHash for storage reauthentication. Rate-limit all test/save/reset attempts and expensive provider calls, not just wrong passwords; check enabled user/tenant and CSRF. No credential/password logging or audit snapshots. Clear sensitive form fields after success; don't persist them to localStorage. If reauth tickets are used, bind tenant/user/session/action, short expiry and revocation. Be explicit that a shared login cannot distinguish staff from owner; separate privilege protection is necessary if staff must not change storage.

7. **Make key rotation real.** Validate strictly decoded 32-byte master keys, 12-byte random IVs, 16-byte tags and bounded envelope fields. Use unambiguous AAD encoding of tenant, connection and version. Maintain active key ID plus read support for retained versions. Fail closed on missing keys/tampering with sanitized errors. Provide an audited re-encryption procedure and separate protected key backup; do not delete old keys until all envelopes and restore paths are accounted for.

8. **Define platform connection versioning.** Platform config also needs stable account identity/version so changing env cloud name does not redirect old assets. Pin files and in-flight uploads to original connections. Atomically switch company active pointer with expectedVersion and audit. Concurrent saves cannot leave ambiguous active connections. Retained connection means no new prepares, but define already-prepared upload completion behavior explicitly (prefer completion against original connection while valid). No silent fallback on custom provider failure. Revoked credentials make that connection unavailable without changing ownership or attempting deletion in another account.

9. **Migration is required.** Backfill existing local and Cloudinary records explicitly before enforcing mandatory connection fields. Existing public Cloudinary assets are not made private just by changing new-upload parameters. Inventory old links, produce a reviewed migration to restricted assets, validate byte/content/access and update references safely; address cached/public URLs and invalidation with provider-supported behavior. Never delete originals before validated replacement and rollback evidence. Files on the old computer must be transferred from a host that can access them; Vercel cannot read that directory.

10. **Separate deletion state from accessibility.** Define DeletePending/DeleteFailed/tombstone lifecycle and retry policy for proven unreferenced files. Don't mark a referenced asset unavailable because cleanup failed. Attach/cleanup use shared transactional claims/reference checks; cleanup operates in bounded batches, leases/retries, pinned connection and verified provider responses. TTL deletion of pending metadata alone is not asset cleanup: preserve cleanup ownership until provider deletion is confirmed. Unique test assets also need tracked cleanup on partial failure. Do not run live cleanup before its race cases pass.

11. **Optimization and abuse bounds.** Index connection tenant/id, active pointer, file tenant/id/connection/status, and pending tenant/user/status/expiry/publicId. Prefer point queries and bounded jobs; no scanning all tenant files on a Settings request. Debounce manual connection tests, show last verified timestamp, add provider timeout/retry with bounded exponential backoff for 429/5xx, and do not retry bad credentials blindly. Cache configuration only with tenant/connection/version keys; never cache authorization or share mutable global SDK credentials across requests. Bound upload quotas and pending count per tenant/user. Secret-bearing requests/responses are no-store. Do not assume local filesystem, Cloudinary or application memory is a durable job queue on Vercel.

12. **Acceptance additions.** Test real deployed 5 MB uploads through each screen; overwrite replay, modified type, oversized/invalid bytes, expire-before-complete, duplicate completion, connection switch during upload, two concurrent connection saves, secret/key rotation, old local asset access, legacy public migration, revoked custom account, attach-vs-delete, provider timeout after upload, test cleanup failure, and unauthorized direct delivery. Check auth login/logout/CSRF after origin changes. Report API tests separately from browser evidence. Cloudinary live smoke tests use isolated generated test assets only and exact cleanup. One final typecheck/build after focused corrections; no repeated full-suite loop.

Remaining product requirements are unchanged: report pagination/full-filter totals, correct return and profit summaries, print/PDF parity, controlled historical catch-up/discrepancy workflows, backup restore, operational monitoring and pilot acceptance. Do not declare these complete as a consequence of this storage pass.
